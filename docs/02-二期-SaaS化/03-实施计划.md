# 二期 SaaS 化实施计划

> 状态：组织与权限、租户赛事收款和啤酒币主要实现已落地，正在进行链路验收
> 最后更新：2026-08-29
> 用途：记录二期开发顺序、依赖、数据库迁移和验收门槛。实际任务开始后持续更新状态。

## 0. 当前实现基线

截至 2026-08-29，后端已完成一期巨型业务门面的第一轮拆分：原 `CompetitionServiceImpl`、`EntryServiceImpl`、`RoundServiceImpl` 已删除，比赛、报名、评审、结果等能力已按业务域和用例职责迁入 `competition`、`registration`、`judging`、`result` 等模块。组织基线迁移已执行，入驻申请、平台审核、账号发放、JWT 后台身份与首次改密、比赛范围校验和受控文件访问已落地。比赛、报名、支付/退款、评审、轮次、奖项、反馈、导出、现场看板和操作日志已完成第一轮组织隔离；租户赛事收款配置、微信收款码受控文件、厂商端读取、报名收款快照、主办方手工确认和租户线下退款链路已落地。啤酒币全局价格设置、动态阶梯计价、独立购买订单、微信 Native/JSAPI 支付、模拟到账、钱包批次、FIFO 流水和赛事两个结算节点已实现，后台入口已接入组织管理并补充赛事详情余额提示；当前剩余工作集中在链路验收、裁判招募和公共主办方展示。

因此，当前不需要再进行一次全后端大规模重构；新增 SaaS 功能不得回填到旧的 `service/impl` 巨型类中。对认证、平台支付、银行转账和奖项文件等直接受 SaaS 影响的遗留大类，按实际功能切片进行局部拆分。

## 1. 实施前提

二期不采用“先把所有表改完，再开始写代码”的方式。正确顺序为：

```text
已确认业务决策
→ 主题详细设计（状态、权限、接口、逻辑表）
→ 增量 SQL 与迁移验证方案
→ 后端、前端和 SQL 按功能切片同步实现
→ 集成测试、浏览器验收、发布演练
```

进入任何编码阶段前，必须满足：

- 本目录中的相关决策和详细设计已确认。
- 新增或变更表已明确字段、索引、数据回填、兼容方式和回滚方案。
- 现有平台自办赛事的兼容策略已写入测试用例。
- 当前工作区的用户已有变更已识别，不覆盖无关文件。

## 3. 关键实施依赖

### 3.1 必须优先完成的底座

组织归属和权限校验已经形成可复用底座。`AuthInterceptor` 负责后台身份、首次改密和成员关系有效性；`CompetitionAccessService` 负责比赛及其关联业务范围；`FileAccessService` 负责文件授权；评委和操作日志有独立的范围入口。啤酒币和租户收款均通过这些边界校验，避免在支付、钱包和结算分支中重新引入跨主办方读取或修改。

已完成的底座交付：

1. 入驻申请提交、状态查询、补充资料和平台超级管理员审核。
2. 审核通过后的企业账户、主办方组织、初始管理员账号和成员关系创建；账号发放失败可重试。
3. 历史啤酒事务局组织、比赛、可追溯文件和操作日志回填。
4. JWT/当前会话中的后台身份、组织范围和首次改密限制。
5. 统一的比赛归属断言、文件访问授权和评委范围服务。
6. 后台列表、详情、导出、文件下载、反馈、日志和写操作的代表性越权测试。

租户收款和啤酒币主要切片已经完成，正式发布前仍需完成：

1. 用两个租户和平台赛事各准备一套验收数据，补齐报名、付款、退款、银行转账、轮次、奖项和文件下载的完整跨组织矩阵。
2. 对啤酒币价格、购买、回调幂等和赛事结算准备验收数据及集成验证。
3. 完成公共赛事主办方展示字段，确保平台自办与第三方赛事的公开页面口径一致。
4. 迁移前确认对象存储敏感前缀为私有；当前本地库仍有 22 条找不到转账/退款业务关联的历史凭证资产，虽已由授权层拒绝下载，正式发布前需备份、复核并执行 `20260824_saas_file_orphan_quarantine.sql` 或等价隔离措施，之后只能通过受控服务访问。

### 3.2 啤酒币与赛事状态的依赖

啤酒币不新增比赛主状态。租户赛事沿用一期的：

```text
DRAFT → REGISTRATION_OPEN → REGISTRATION_CLOSED → JUDGING_PREP
```

在两个既有动作中加入结算门槛：

- `DRAFT → REGISTRATION_OPEN`：租户赛事检查可用啤酒币并扣除最低 1 枚。
- `REGISTRATION_CLOSED → JUDGING_PREP`：主办方确认有效酒款，结算并扣除差额；不足时阻断进入评审准备。

二维码、正式分组、第一轮创建和裁判任务发布还需校验赛事已完成对应结算，避免绕过状态入口。

### 3.3 支付改造的兼容边界

报名费支付按比赛所属主办方分支处理：

- 平台自办赛事：保留一期微信 Native/JSAPI、银行转账、支付回调和退款服务。
- 租户赛事：展示本场收款配置，主办方手工确认；不走平台微信报名支付回调。
- 啤酒币购买：统一由平台收款，复用平台微信支付能力，但使用独立的啤酒币订单模型，不能复用参赛报名订单。

## 4. 数据库迁移与兼容安排

### 4.1 迁移策略

- 继续采用“完整建库基线 + 日期命名增量 SQL + 手工执行验证”的现有发布方式，暂不在本阶段引入自动迁移框架。
- 每一批 SQL 必须在本地空库、一期已有测试数据和待部署环境备份副本上验证。
- 先执行只新增表/字段/索引和数据回填的兼容迁移，再部署兼容新旧字段的代码；确认稳定后才允许收紧旧流程。
- 当前系统尚处测试期，远程数据库没有有价值业务数据；仍按生产级备份、回滚和验证步骤执行。

### 4.2 首次迁移内容

首次迁移应完成以下可逆基础项：

1. 创建入驻申请、企业账户、主办方组织和主办方管理员关系表。
2. 创建啤酒事务局平台组织和关联企业账户。
3. 为现有后台账号标记平台身份；为所有历史比赛回填平台组织归属。
4. 为 `competition` 增加组织归属及索引。
5. 为文件和操作日志补充可追溯的组织范围字段或查询路径。

迁移完成后，旧比赛在新代码中必须表现为平台自办赛事，支付和评审流程不得变化。

## 5. 测试、上线与验收

### 5.1 必测场景

- 未登录申请人可以提交入驻申请、查询状态和补充资料，但不能访问后台接口。
- 只有平台超级管理员可以查看、审核和发放主办方账号；其他后台身份不能越权处理申请。
- 审核拒绝必须保留原因；需要补充资料的申请可以重新提交，状态变化可追溯。
- 审核通过和账号发放具备幂等性，重复操作不会创建重复组织、企业账户或管理员账号。
- 审核通过后的账号发放事务失败时申请仍可重试；初始用户名唯一，初始密码只作为一次性交付凭据，首次登录必须改密，日志和数据库不出现明文密码。
- 初始主办方管理员可以在本组织内添加同权限管理员，不能操作其他组织或入驻申请；平台超级管理员可以跨组织重置和停用管理员。
- 平台赛事管理员无法查询、导出、下载或修改租户赛事数据。
- 租户 A 无法通过列表参数、资源 ID、文件地址或导出接口访问租户 B 数据。
- 平台自办赛事仍可发起微信自动支付、接收回调并执行现有退款流程。
- 租户赛事只展示主办方配置的收款方式，付款确认由主办方完成。
- 啤酒币全局价格修改后立即用于新订单，已创建未支付订单继续使用下单快照；回调重复到达时只入账一次，结算重复提交时只扣减一次。
- 最早到期批次优先扣减；余额不足时无法开放报名或进入评审准备。
- 锁定后新增酒款达到新档位时必须先补扣；取消酒款不自动退币。
- 裁判仅能申请开放招募赛事；主办方只能查看申请本场赛事的裁判。
- 公共页面显示第三方赛事及其实际主办方。

### 5.2 浏览器验收

- 公开入驻表单、申请状态和补充资料流程按桌面全屏尺寸验收。
- 主办方后台和厂商端按桌面全屏尺寸验收，覆盖侧边栏、表格、筛选区、表单和关键操作。
- Judge H5 按手机竖屏比例验收招募、申请、任务列表和评分流程。
- 平台自办和租户赛事各准备一套完整验收数据，避免仅验证单一路径。

### 5.3 发布顺序

1. 备份目标数据库。
2. 执行增量 SQL 并验证结构、回填数量和关键索引。
3. 发布兼容代码。
4. 用平台超级管理员、平台赛事管理员、两个租户管理员、申请人、厂商和裁判账号做权限冒烟验证。
5. 在测试模式验证啤酒币购买、模拟到账和赛事结算；真实微信模式验证 Native/JSAPI 回调分流。
6. 出现阻断问题时，停止新功能入口；依据迁移脚本的回滚说明恢复数据或禁用新组织。
