# 租户收款与啤酒币设计

> 状态：已确认业务规则，待实施级接口与字段评审  
> 对应决策：`SaaS-ADR-005` 至 `SaaS-ADR-010`  
> 适用范围：报名费收款、退款记录、在线购币、企业钱包、赛事结算和评审门槛。

## 1. 双模式资金边界

| 场景 | 平台自办赛事 | 租户 SaaS 赛事 |
| --- | --- | --- |
| 报名费收款主体 | 啤酒事务局 | 实际主办方 |
| 厂商付款方式 | 延续一期微信 Native/JSAPI、银行转账和模拟支付 | 微信收款码、银行转账，可按比赛组合启用 |
| 付款确认 | 微信回调自动确认或后台银行转账确认 | 主办方管理员手工确认 |
| 退款 | 保留一期退款申请和微信退款 | 主办方线下退款，平台记录处理结果 |
| 平台服务费 | 现有一期规则 | 不从报名费抽成 |
| 啤酒币 | 不扣减 | 发布和评审准备时扣减 |

租户赛事的报名费和啤酒币购买是两类不同资金流：

- 报名费归主办方，平台不代收。
- 啤酒币购买归平台，平台使用现有微信支付能力收款并在支付成功后自动入账。

不得复用报名批次 `payment_order` 作为啤酒币购买订单。两者的收款主体、业务对象、状态、退款规则和审计要求不同。

## 2. 租户报名费收款

### 2.1 比赛级配置

租户主办方在每场比赛中配置收款方式：

| 配置项 | 规则 |
| --- | --- |
| 微信收款码 | 可选；上传二维码图片，由参赛厂商扫码向主办方付款 |
| 银行账户名 | 启用银行转账时必填 |
| 银行账号 | 启用银行转账时必填 |
| 开户行 | 启用银行转账时必填 |
| 启用方式 | 至少启用一种；可同时启用两种 |
| 收款提示 | 可选，向参赛厂商说明付款备注、时限或联系方法 |

收款配置应作为比赛配置的一部分。参赛厂商提交报名后，系统保存当前收款配置快照，避免主办方后续改卡号或换码影响历史报名的付款依据。

### 2.2 厂商端流程

```text
提交一款或多款酒
→ 创建待确认报名记录
→ 查看本场比赛收款方式
→ 向主办方付款
→ 银行转账时可提交凭证
→ 等待主办方确认
→ 确认后报名生效、标签和送样能力按一期规则开放
```

微信收款码付款不强制上传凭证。银行转账由厂牌上传付款凭证，凭证为必填，转账备注选填；付款账户名和转账时间不再要求厂牌重复录入，主办方以付款凭证和系统提交时间核对到账并确认或驳回。为兼容既有数据库约束，后端在厂牌未提供转账时间时将凭证提交时间写入 `transfer_time`，该字段不再作为实际转账时间展示或统计依据。

### 2.3 主办方处理边界

- 主办方管理员只能确认本组织赛事的报名付款。
- 手工确认必须记录操作者、时间、备注和原状态。
- 对租户赛事，确认动作的含义是“主办方确认该报名可继续”，不代表平台完成资金核验。
- 参赛报名在未确认前不应进入有效酒款口径、分组或评审。

### 2.4 退款与取消

租户赛事中，退款实际在线下完成。系统提供受审计的处理动作：

| 动作 | 业务效果 |
| --- | --- |
| 标记已退款并取消报名 | 记录主办方、时间、备注；酒款不再属于有效报名 |
| 取消未确认报名 | 无需退款资金动作；酒款不进入评审 |
| 驳回取消申请 | 保留当前报名状态及处理说明 |

租户路径不得调用一期微信退款服务。平台自办赛事继续按现有退款申请、处理和微信回调链路运行。

## 3. 啤酒币账户与在线购买

### 3.1 账户归属

啤酒币属于通用企业账户，主办方组织只是当前能够使用该企业账户办赛的主体。二期中企业账户仅服务租户赛事；未来酒款评测平台直接复用同一账户、批次和流水。

### 3.2 购买流程

```text
主办方管理员选择啤酒币商品
→ 创建啤酒币购买订单
→ 使用平台微信支付
→ 平台支付回调验证成功
→ 创建到账批次
→ 写入充值流水
→ 钱包可用余额增加
```

商品至少需要配置名称、售价、到账啤酒币数量、启用状态和展示排序。购买订单必须保存商品和金额快照，避免商品价格后续调整影响历史账务。

支付回调必须以购买订单号和微信交易号保证幂等。重复回调只能创建一次到账批次和一次充值流水。

### 3.3 有效期与余额

- 每个到账批次自到账成功之日起有效 1 年。
- 可用余额仅统计未过期、未用尽批次的剩余数量。
- 消费时按到期日从早到晚扣减；到期日相同再按到账时间和批次 ID 排序。
- 啤酒币不可转让，不允许普通用户退款。
- 平台超级管理员可做人工补发、冲正或到期修正；每次必须写明原因和审计记录。

余额不应仅保存为可直接覆盖的单一数值。结算依据必须来自到账批次、账务流水和扣减分摊，余额可由这些事实汇总得到或作为受校验的缓存字段。

## 4. 赛事结算规则

### 4.1 首次扣减：开放报名

仅租户赛事执行：

```text
DRAFT
→ 检查可用啤酒币是否至少为 1
→ 原子扣减 1 枚并生成“发布最低消费”结算记录
→ REGISTRATION_OPEN
```

余额不足时，不得开放报名。发布扣除的 1 枚计入整场赛事最终应消耗量，即使最终没有有效报名也不退回。

### 4.2 最终核算：进入评审准备

主办方在报名截止后确认有效酒款，再推动比赛进入 `JUDGING_PREP`：

```text
最终应消耗 = max(1, ceil(有效酒款数 / 10))
本次应补扣 = 最终应消耗 - 已累计扣减
```

有效酒款指当前比赛中：

- 由主办方确认可参加比赛；
- 未取消、未删除；
- 可以进入正式评审分组的酒款。

具体实现中必须使用一个明确、可查询的状态或标记作为有效口径，不能只依赖前端筛选或金额字段推断。

结算成功后写入：有效酒款数量、计费档位、累计应消耗、实际补扣数量、结算时间、操作者、所锁定的酒款清单和扣减流水关联。余额不足时，比赛保持 `REGISTRATION_CLOSED`，不得进入评审准备。

### 4.3 锁定后的增量

| 变化 | 处理规则 |
| --- | --- |
| 新增酒款但未跨计费档位 | 可保存；进入分组前仍需检查当前结算锁定规则 |
| 新增酒款跨越计费档位 | 创建增量结算，扣币成功后才可分组或生成该酒款正式标签 |
| 删除或取消已锁定酒款 | 不自动退币；保留原结算和操作审计 |
| 人工特殊退币 | 仅平台超级管理员可操作，必须产生冲正流水和原因 |

## 5. 结算门槛与既有流程衔接

| 既有动作 | 平台自办赛事 | 租户赛事 |
| --- | --- | --- |
| 开放报名 | 原有配置检查 | 原有配置检查 + 最低 1 枚啤酒币扣减 |
| 关闭报名 | 原有逻辑 | 原有逻辑 |
| 进入评审准备 | 原有检查 | 原有检查 + 确认有效酒款 + 结算差额 |
| 正式分组、创建第一轮 | 原有权限与状态检查 | 额外要求赛事结算已锁定且无待补扣 |
| 生成正式二维码/标签 | 原有逻辑 | 额外校验对应酒款已纳入有效结算范围 |
| 安排裁判任务 | 原有逻辑 | 额外校验赛事已完成评审准备结算 |

不得仅在前端禁用按钮。上述门槛必须在后端 Service 层再次校验，并在同一事务中完成状态变更、扣减和审计。

## 6. 并发、幂等与审计要求

- 同一购买订单的支付回调重复到达，充值只成功一次。
- 同一赛事的发布扣减和结算扣减使用稳定业务幂等键，重复请求不能重复扣币。
- 扣减批次时锁定余额来源，避免两个赛事并发消费同一批啤酒币。
- 购买订单、到账批次、每笔流水、扣减分摊、赛事结算均应能相互追溯。
- 任意人工调整都记录平台超级管理员、调整方向、数量、原因和关联对象。

## 7. 开发前仍需细化的实施输入

以下项目不改变已确认业务规则，但在实现在线购买前必须补充：

- 啤酒币商品档位、人民币售价、是否允许一次购买多件。
- 啤酒币购买仅支持微信 Native、JSAPI，还是两者都支持。
- 购买发票、客服咨询和支付超时展示文案。
- 收款二维码图片的尺寸、格式和替换规则。
- 租户赛事中“主办方确认有效酒款”的后台操作入口和二次确认文案。
