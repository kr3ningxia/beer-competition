# 二期 SaaS 化数据库改动明细

> 状态：设计建议，尚未形成或执行迁移 SQL  
> 最后核对：2026-07-27  
> 依据：本地 `beer_competition` 当前 40 张表的实际字段与索引、一期支付/评审逻辑、已确认的 SaaS 业务规则。  
> 关联文档：[数据库迁移设计](04-数据库迁移设计.md)、[组织权限与数据隔离](01-组织、权限与数据隔离.md)、[租户收款与啤酒币](02-租户收款与啤酒币.md)。

## 1. 结论

二期的数据库改造重点有四个：

1. 为比赛建立主办方归属，使系统能可靠区分啤酒事务局自办赛事和第三方租户赛事。
2. 为后台账号建立平台/主办方身份和组织关系，使查询、导出、文件下载、付款确认和评审操作具备数据范围。
3. 在不破坏一期微信自动支付的前提下，让租户赛事使用主办方收款码、银行卡和手工确认。
4. 新增独立的啤酒币钱包、购买、批次、流水、结算与裁判招募数据域。

不建议给所有现有业务表都增加 `organizer_id`。当前多数业务记录已通过 `competition_id` 关联比赛，比赛再关联主办方即可完成隔离。重复写入组织 ID 会增加数据漂移风险。

## 2. 平台自办赛事与租户赛事的数据库判定

推荐的判定链路：

```text
competition.organizer_id
→ organizer.organizer_type
→ 决定报名费支付、退款和啤酒币规则
```

| `organizer.organizer_type` | 比赛性质 | 厂商报名费支付 | 啤酒币 |
| --- | --- | --- | --- |
| `PLATFORM` | 啤酒事务局自办赛事 | 沿用一期微信 Native/JSAPI、银行转账、微信退款 | 不扣减 |
| `TENANT` | 第三方主办方赛事 | 主办方微信收款码和/或银行账户，主办方手工确认 | 按发布和评审准备规则扣减 |

这样能够直接调度当前微信自动支付：后端创建报名支付订单时，先读取比赛及主办方类型。

```text
PLATFORM
→ 允许调用当前 WechatPaymentService / BatchPaymentService
→ 创建现有 payment_order 与微信交易单

TENANT
→ 禁止创建平台微信报名支付订单
→ 返回 competition_collection_config 中的主办方收款信息
→ 等待主办方手工确认 entry_payment
```

这个判断必须存在于后端 Service 层；前端隐藏按钮只改善体验，不能承担资金与权限边界。

## 3. 当前库中与二期直接相关的现状

| 表 | 当前情况 | SaaS 改造问题 |
| --- | --- | --- |
| `competition` | 有比赛状态、费用、送样信息，无组织字段 | 无法判断比赛是谁主办，也无法隔离后台数据 |
| `admin_user` | 仅用户名、密码、姓名、状态 | 无平台/主办方身份，无组织范围 |
| `payment_order` | 报名批次聚合订单，含微信交易字段 | 资金模型默认是平台收款 |
| `entry_payment` | 单酒款支付，已有人工确认人和备注 | 可复用手工确认能力，但需区分确认主体和付款方式 |
| `bank_transfer_payment` | 有比赛、厂商、凭证、处理人和备注 | 可复用，但缺少收款账户历史快照 |
| `entry_refund` | 深度包含微信退款号和回调字段 | 租户线下退款需有明确处理方式 |
| `file_asset` | 泛化文件归属，无主办方范围 | 直接文件 ID 下载时难以防跨主办方访问 |
| `admin_operation_log` | 按操作对象字符串记录 | 不方便按主办方、比赛做权限查询和审计 |
| `judge_account` | 统一评委资料库，联系方式已加密 | 无裁判招募资料授权记录 |
| `competition_judge_assignment` | 比赛级评委/基础桌分配 | 无法追溯正式分配是否来自招募录用 |

当前库没有物理外键。二期继续使用应用层关联和事务校验，但每个新增 `*_id` 都必须有索引、归属校验和孤儿数据检查 SQL。

## 4. 必须修改的已有表

### 4.1 `competition`

当前关键字段：`id`、`code`、`status`、`entry_fee`、报名时间、送样信息。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `organizer_id` | `bigint not null` | 比赛的实际主办方，是二期所有租户隔离、资金分流和公开展示的根字段。 |

建议索引：

```sql
create index idx_competition_organizer_status_deadline
    on competition (organizer_id, status, registration_deadline);
```

它的实际作用：

- 主办方管理员比赛列表只查询本组织。
- 报名、酒款、付款单、评审桌、奖项等资源先通过比赛查主办方，再验证当前账号。
- 判断 `PLATFORM` 时，继续使用一期微信自动支付；判断 `TENANT` 时，使用租户收款配置和啤酒币。
- 公共赛事、结果和裁判招募页通过关联 `organizer` 显示实际主办方。

不建议新增 `tenant_flag`、`self_hosted_flag`、`payment_mode` 等重复字段。它们可从主办方类型和比赛级收款配置得到，重复存储会制造不一致。

### 4.2 `admin_user`

当前字段只有：`username`、`password`、`name`、`status`、创建和更新时间。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `admin_type` | `varchar(32) not null` | 标识后台账号的操作身份：`PLATFORM_SUPER_ADMIN`、`PLATFORM_EVENT_ADMIN`、`ORGANIZER_ADMIN`。 |

建议索引：

```sql
create index idx_admin_user_type_status on admin_user (admin_type, status);
```

不建议在此表再增加 `organizer_id` 作为唯一关系来源。主办方管理员归属应该由新表 `organizer_member` 保存；这样不会在账号表和成员表重复维护同一组织 ID。

### 4.3 `file_asset`

当前字段：`business_type`、`owner_type`、`owner_id`、`storage_path`、`public_url`。它可记录文件属于某个对象，但无法快速确定文件所属主办方。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `organizer_id` | `bigint null` | 文件所属主办方范围；历史文件迁移时回填平台组织。 |

建议索引：

```sql
create index idx_file_asset_organizer_owner
    on file_asset (organizer_id, owner_type, owner_id);
```

适用文件包括主办方 Logo、租户收款二维码、银行转账凭证、比赛证书等。下载接口仍需先校验对应业务资源的组织归属，`organizer_id` 是额外的范围和审计依据。

### 4.4 `admin_operation_log`

当前使用 `target_type` 与字符串 `target_public_id` 追溯操作对象，适合通用日志，但不利于按主办方与比赛查询。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `organizer_id` | `bigint null` | 操作所属主办方范围。 |
| `competition_id` | `bigint null` | 比赛相关操作的结构化比赛 ID。 |

建议索引：

```sql
create index idx_admin_log_organizer_time
    on admin_operation_log (organizer_id, create_time, id);
create index idx_admin_log_competition_time
    on admin_operation_log (competition_id, create_time, id);
```

这样可审计“谁给哪个租户确认了付款”“哪场比赛什么时候补扣啤酒币”“谁录用了裁判”。原有通用字段继续保留，不需要替换。

## 5. 报名收款和退款已有表调整

### 5.1 `payment_order`

该表是报名批次的聚合订单，当前已有 `amount`、`status`、`pay_method`、微信交易号、`code_url` 等字段。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `collection_snapshot_json` | `json null` | 保存厂商提交报名时看到的收款信息：启用方式、微信收款码文件、银行账户、开户行、提示文案。 |

建议扩展 `pay_method` 的取值：

```text
WECHAT                 平台自办赛事的平台微信自动支付
BANK_TRANSFER          银行转账
MANUAL_WECHAT_QR       租户赛事主办方微信收款码
MOCK                    测试环境模拟支付
```

作用：主办方修改银行卡或收款码后，历史报名仍可还原当时的付款依据；租户报名也不会误调用平台微信支付。

### 5.2 `entry_payment`

该表已有：`status`、`pay_method`、`confirmed_by_admin_id`、`confirm_remark`、`paid_time`。

建议保持结构，以现有人工确认字段承载租户付款确认：

- `MANUAL_WECHAT_QR`：主办方确认其已线下收款。
- `BANK_TRANSFER`：主办方确认银行转账到账。
- `WECHAT`：仅平台自办赛事由平台微信回调自动确认。

通常不需要额外增加 `organizer_id`，因为它可经 `beer_entry → competition → organizer` 追溯。确认接口必须先验证当前管理员可管理该比赛。

### 5.3 `bank_transfer_payment`

当前已经有 `competition_id`、`amount`、付款人、转账时间、凭证文件、处理人和处理备注，适合继续用于租户银行转账。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `payee_snapshot_json` | `json null` | 保存厂商提交付款凭证时的收款账户名、账号、开户行快照。 |

作用：主办方后续变更银行卡时，仍可明确厂商当时依据何种账户信息转账。现有 `(competition_id, status)` 索引可继续满足主办方待确认列表。

### 5.4 `entry_refund`

当前表中包含微信退款号、退款回调原文等平台自动退款字段。租户赛事仍可复用此表记录退款事实，但应显式区分处理方式。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `refund_method` | `varchar(32) null` | `WECHAT_ORIGINAL` 或 `OFFLINE_ORGANIZER`。 |
| `offline_refund_reference` | `varchar(128) null` | 可选记录线下退款转账单号或备注。 |

作用：平台自办赛事继续微信退款；租户赛事只记录主办方已线下退款，不会调用平台退款接口。

## 6. 裁判相关已有表调整

### 6.1 `judge_account`

当前评委联系方式已使用加密和哈希字段，姓名、资质、利益冲突、审核状态也已存在；它应继续作为跨比赛、跨主办方的统一裁判资源库。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `recruitment_visible_flag` | `tinyint not null default 1` | 是否允许在公开招募中向申请赛事主办方展示资料。 |
| `recruitment_consent_time` | `datetime null` | 记录资料可用于赛事招募的授权时间。 |

这些字段不等于公开手机号或微信号。联系方式仍应在 Service 层按申请关系、录用状态和业务必要性控制解密展示。

### 6.2 `competition_judge_assignment`

当前字段为：`competition_id`、`base_table_id`、`judge_account_id`、`role`。

建议新增：

| 字段 | 建议定义 | 作用 |
| --- | --- | --- |
| `recruitment_application_id` | `bigint null` | 记录正式评审分配来源于哪一份裁判招募申请。 |

建议索引：

```sql
create index idx_judge_assignment_recruitment_application
    on competition_judge_assignment (recruitment_application_id);
```

它只用于追溯，不取代原有的评审桌、角色、轮次任务和状态校验。一期直接邀请评委时该字段为空。

## 7. 不建议改动的已有表

| 表或数据域 | 原因 |
| --- | --- |
| `brewery`、`portal_account` | 它们是参赛厂牌与联系人，不是主办方。一个厂牌应能参加不同主办方比赛。 |
| `registration_batch`、`beer_entry` | 均已有 `competition_id`，不应重复添加组织字段。结算锁定使用独立快照表。 |
| `competition_category`、风格、报名字段、评分表、奖项规则 | 全部以 `competition_id` 隔离，当前模型适合多赛事复用。 |
| 送样、标签、轮次、评审桌、评分、结果、奖项表 | 都是比赛子域，通过比赛归属隔离。 |
| 公共风格库表 | 由平台统一维护，不归属主办方。 |
| `wechat_pay_notify` | 现有 `business_type` 可扩展啤酒币购买支付回调，例如 `BEER_COIN_PURCHASE`；通常无需再建回调审计表。 |

## 8. 必须新增的数据表

### 8.1 组织和企业账户

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `enterprise_account` | `code`、`name`、`status` | 啤酒币的通用归属主体，未来酒款评测平台复用。 |
| `organizer` | `enterprise_account_id`、`name`、`organizer_type`、`status`、`logo_asset_id` | 主办方组织；类型为 `PLATFORM` 或 `TENANT`。 |
| `organizer_member` | `organizer_id`、`admin_user_id`、`status` | 主办方管理员的组织关系。 |

关键约束建议：

```sql
unique (organizer_id, admin_user_id)
```

若二期严格限制主办方管理员只属于一个主办方，再增加：

```sql
unique (admin_user_id)
```

### 8.2 比赛收款配置

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `competition_collection_config` | `competition_id`、`wechat_qr_asset_id`、银行账户名/账号/开户行、`enabled_methods_json`、`collection_note` | 每场租户赛事配置可用收款方式。 |

建议唯一约束：

```sql
unique (competition_id)
```

平台自办赛事不需要该表记录也可继续支付；租户赛事在开放报名的配置检查中必须至少存在一种启用收款方式。

### 8.3 啤酒币在线购买与钱包

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `beer_coin_product` | 商品编码、售价、到账数量、状态 | 在线购买商品。 |
| `beer_coin_purchase_order` | 订单号、企业账户、商品快照、金额、微信交易号、状态 | 啤酒币购买支付订单。 |
| `beer_coin_lot` | 批次号、总数、剩余数、到账日、到期日 | 每次到账形成的可消耗批次。 |
| `beer_coin_ledger` | 流水号、方向、数量、业务类型、业务 ID、幂等键 | 不可变账务事实。 |
| `beer_coin_consumption_allocation` | 扣减流水、到账批次、数量 | 记录一笔消费从哪些批次扣减，实现最早到期优先。 |

核心索引：

```sql
beer_coin_purchase_order: unique(order_no), unique(out_trade_no)
beer_coin_lot: unique(lot_no), index(enterprise_account_id, expires_at, remaining_quantity)
beer_coin_ledger: unique(ledger_no), unique(enterprise_account_id, idempotency_key)
beer_coin_consumption_allocation: unique(ledger_id, lot_id)
```

### 8.4 赛事啤酒币结算

| 表 | 关键字段 | 作用 |

| `competition_coin_settlement` | `competition_id`、结算类型、有效酒款数、计费档位、本次扣减、关联流水、幂等键 | 记录发布最低消费、报名截止补扣和新增酒款补扣。 |
| `competition_coin_settlement_entry` | `settlement_id`、`beer_entry_id`、状态快照 | 锁定某次结算纳入计费的酒款集合。 |

结算类型建议：

```text
PUBLISH_MINIMUM
REGISTRATION_CLOSE
INCREMENTAL
MANUAL_ADJUSTMENT
```

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `judge_recruitment` | 比赛、开放状态、招募窗口、地点、要求 | 赛事裁判招募配置。 |
| `judge_recruitment_session` | 招募、日期、起止时间、名称 | 供裁判选择的可参加场次。 |

## 9. 首次迁移与历史数据回填

首次 SQL 应按以下顺序执行：

1. 新建 `enterprise_account`、`organizer`、`organizer_member`。
2. 创建“啤酒事务局”企业账户和 `PLATFORM` 主办方组织。
3. 给 `competition` 增加可空 `organizer_id`，将全部历史比赛回填平台组织，再收紧为 `not null`。
4. 给 `admin_user` 增加 `admin_type`，将已有账号回填平台身份。
5. 增加组织相关索引。
6. 发布能够同时兼容旧数据与新组织字段的后端代码。
7. 再创建租户组织、租户管理员和第一场租户赛事。

历史比赛迁移后必须验证：

```text
所有 competition.organizer_id 非空
所有历史比赛属于 PLATFORM 组织
平台自办赛事仍可创建微信报名支付订单
旧报名、退款、评审、奖项数据可按 competition_id 正常查询
```

## 10. 数据库不能单独完成的事项

数据库提供归属、配置、状态和审计依据；以下规则必须由后端事务实现：

- 当前后台管理员是否可访问某比赛、酒款、付款单或文件。
- 平台赛事允许微信自动支付，租户赛事禁止调用平台报名支付接口。
- 微信购买啤酒币的回调幂等。
- 最早到期啤酒币批次的并发扣减。
- 赛事发布扣 1 枚、进入评审准备补扣差额、锁定后新增酒款补扣。
- 主办方手工确认报名费后，酒款才进入有效报名和结算口径。

因此，数据库迁移和后端改造必须按同一功能切片上线，不能仅执行加字段 SQL 后就开放租户入口。
