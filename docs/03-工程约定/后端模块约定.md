# 后端模块约定

> 状态：当前有效工程约定  
> 适用工程：`beer-competition-api`

后端当前是按接口使用方和技术职责组织的 Spring Boot 单体应用：

```text
com.beercompetition
├─ controller
│  ├─ admin
│  ├─ judge
│  ├─ pay
│  ├─ portal
│  ├─ publicapi
│  └─ support
├─ service
│  ├─ impl
│  │  └─ round
│  └─ support
├─ mapper
├─ pojo
│  ├─ dto
│  ├─ enums
│  ├─ po
│  └─ vo
├─ pay
├─ common
├─ config
├─ properties
├─ scheduler
├─ security
└─ storage
```

## 职责约定

- `controller` 负责参数接收、鉴权入口和统一响应，不承载复杂业务编排。
- `service/impl` 负责业务流程、事务、权限边界和状态校验。
- `service/support` 放置被多个业务服务复用的业务辅助能力。
- `mapper` 负责数据库读写，避免在 Mapper 中拼装跨领域业务流程。
- `pojo/dto` 用于请求参数，`pojo/vo` 用于响应，`pojo/po` 对应数据库表。
- `pojo/enums` 保存有明确业务语义的状态和类型，前后端应按枚举口径对齐。
- `pay` 封装微信支付客户端及运行模式，支付通知入口位于 `controller/pay`。
- `security` 负责 JWT、角色和接口访问控制。
- `storage` 提供文件存储抽象，业务代码不直接绑定本地磁盘或 OSS 实现。
- `properties` 保存应用配置映射，避免在业务代码中直接散落环境变量名称。
- `scheduler` 只放置定时触发入口，实际业务仍委托给 Service。

## 变更原则

- 优先延续当前结构，单个需求不随意引入新的分层体系。
- 新增接口先判断属于后台、厂商、评审、公共认证还是支付通知。
- 涉及多个状态变更时，在 Service 层明确事务边界并记录必要操作日志。
- 涉及手机号、微信号等隐私字段时统一使用 `PiiService`。
- 二期 SaaS 化需要调整分层或模块边界时，先在二期详细设计或决策记录中确认。
