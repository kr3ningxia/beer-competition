# 后端模块约定

> 状态：当前有效工程约定  
> 适用工程：`beer-competition-api`

后端采用模块化单体。Controller 按接口使用方组织，核心业务按业务域和用例职责组织；一期尚未迁移的稳定能力继续保留在 `service`，按后续需求逐步收口。

## 职责约定

- `controller` 负责参数接收、鉴权入口和统一响应，不承载复杂业务编排。
- `competition` 负责比赛创建、配置、状态流转和比赛聚合查询。
- `registration` 负责报名、送样、报名支付管理和退款流程。
- `judging` 负责轮次编排、评委任务、评分确认和排名确认。
- `result` 负责厂商端及公开端的结果查询和证书读取。
- `organization` 负责入驻申请、审核后的组织开通和主办方账号生命周期。
- `billing` 负责啤酒币等独立账务事实，比赛模块只通过结算接口协作。
- `file` 负责文件元数据归属和访问权限；`storage` 只负责底层字节存取。
- `audit` 负责跨业务域的操作审计写入和按身份范围查询。
- 每个业务模块优先按命令、查询、配置、生命周期等真实用例拆分接口；Controller 只依赖所需的细粒度接口。
- `service/impl` 暂时承载尚未迁移的业务流程，以及多个模块共同使用的一期能力；原 `CompetitionServiceImpl`、`EntryServiceImpl`、`RoundServiceImpl` 已删除并完成第一轮模块化拆分，新增二期功能不得继续堆入现有遗留大类。
- `service/support` 放置被多个业务服务复用的业务辅助能力。
- `service/impl/round` 保存轮次模块共享的查询支持、校验策略和常量，不对 Controller 暴露。
- `mapper` 负责数据库读写，避免在 Mapper 中拼装跨领域业务流程。
- `pojo/dto` 用于请求参数，`pojo/vo` 用于响应，`pojo/po` 对应数据库表。
- `pojo/enums` 保存有明确业务语义的状态和类型，前后端应按枚举口径对齐。
- `pay` 封装微信支付客户端及运行模式，支付通知入口位于 `controller/pay`。
- `security` 负责 JWT、角色和接口访问控制。
- `storage` 提供文件存储抽象，业务代码不直接绑定本地磁盘或 OSS 实现。
- `properties` 保存应用配置映射，避免在业务代码中直接散落环境变量名称。
- `scheduler` 只放置定时触发入口，实际业务仍委托给 Service。

## 模块依赖规则

- 调用方向保持为 `controller/scheduler -> 业务模块接口 -> 模块实现及 Mapper`。
- 跨模块协作通过对方公开的业务接口完成，避免直接注入其他模块的 Mapper。
- 查询组装器可以批量读取同一用例所需数据，但不能修改业务状态。
- 事务放在完成一个业务动作的公开服务方法上；纯查询和对象组装不机械添加事务。
- 接口按调用方需要暴露，避免重新出现同时包含创建、查询、状态流转、支付和文件处理的统一大接口。

## 二期 SaaS 接入位置

二期组织表结构和可信后台身份已经通过批次 A 迁移落地。后续新增能力仍不得默认放行或信任请求参数中的组织 ID；范围校验必须在应用服务入口完成，并在列表/分页 Mapper SQL 中保留组织条件。按以下边界接入：

| 能力 | 建议位置 | 接入规则 |
| --- | --- | --- |
| 主办方与账号开通 | `organization/application` | `OrganizerProvisioningService` 在账号发放事务中幂等创建企业账户、主办方、管理员和成员关系；审核动作与账号发放保持两个独立用例。 |
| 比赛权限与数据范围 | `competition/access` | `CompetitionAccessService` 从已认证后台账号解析可信主办方范围；比赛、报名、评审、导出和文件用例在服务入口调用，Controller 传入的组织 ID 不作为授权依据。 |
| 文件元数据与访问 | `file`，底层继续使用 `storage` | `FileAccessService` 负责文件元数据、业务归属和读取授权。下载必须先校验关联比赛或主办方，再读取存储对象。 |
| 报名支付分流 | `registration/payment` | `CompetitionPaymentPolicy` 根据比赛所属主办方类型选择平台自动支付或租户线下收款流程；支付 Controller 不直接判断主办方类型。 |
| 啤酒币购买与结算 | `billing/beercoin` | 购买订单、到账批次、流水和赛事分摊形成独立账务模块；比赛生命周期只调用 `BeerCoinSettlementService`，扣减使用唯一业务键、数据库锁和独立集成测试保证幂等。 |

一期平台赛事继续走现有支付、退款和文件链路。二期能力按完整业务切片接入，每个切片同时包含表结构、可信身份、服务校验和越权测试，避免只加字段或只加接口。

## 代码规模与注释

- 单个 Java 文件超过 500 行时检查职责；接近或超过 800 行时优先按真实用例或组装职责拆分。
- 当前 500 行以上文件主要包含一期支付、认证、评分、奖项和聚合查询等遗留能力；不要求为满足行数阈值进行机械拆分，但在 SaaS 直接改造这些能力时，必须优先按独立业务用例收口。
- `CompetitionServiceImpl`、`EntryServiceImpl`、`RoundServiceImpl` 等旧巨型门面已不再存在；架构测试持续防止其重新进入类路径。
- 依赖数量较多但只服务一个聚合查询时可以保留；若依赖来自多个独立业务动作，应继续拆分。
- 公共业务接口和复杂模块入口使用中文 Javadoc，说明职责、权限或副作用。
- 方法内注释重点说明事务、状态约束、幂等、兼容和批量加载原因，不逐行翻译代码。

## 变更原则

- 优先延续当前结构，单个需求不随意引入新的分层体系。
- 新增接口先判断属于后台、厂商、评审、公共认证还是支付通知。
- 涉及多个状态变更时，在 Service 层明确事务边界并记录必要操作日志。
- 涉及手机号、微信号等隐私字段时统一使用 `PiiService`。
- 二期 SaaS 化需要调整分层或模块边界时，先在二期详细设计或决策记录中确认。
